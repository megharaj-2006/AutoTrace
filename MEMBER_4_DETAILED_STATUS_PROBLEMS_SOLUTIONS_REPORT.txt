1.2 Security Actuator Daemon (services/actuator-security/ — Port 8081)
--------------------------------------------------------------------------------
- Built an independent, high-performance daemon using Python 3.11+ and FastAPI.
- Implemented core REST endpoints:
  * POST /api/v1/quarantine: Disconnects compromised container from autotrace-mesh.
  * POST /api/v1/release: Authenticated recovery endpoint to reconnect containers.
  * GET /health: Liveness probe returning status, dry-run state, and Docker connectivity.
  * GET /ready: Readiness probe (fails 503 if live mode without Docker).
  * GET /api/v1/quarantine/status: Lists active quarantined container IDs.
- Core Engine Architecture:
  * services/actuator-security/src/containment.py: Uses official Docker Python SDK
    (`docker.from_env()`). ZERO subprocess shell calls, eliminating command injection.
  * 5-step containment verification: Idempotency check -> Container existence check ->
    Network membership verification -> Force disconnect -> Post-disconnect verification.
  * High-precision timing: Uses nanosecond monotonic clock (`time.perf_counter_ns()`)
    to measure real execution duration and benchmark against the <2000ms target.
  * Thread-safe quarantine state tracking with mutex locks.
  * Safe dry-run mode enabled by default (`ACTUATOR_DRY_RUN=true`).
- Input Sanitization & Schemas:
  * services/actuator-security/src/models.py: Pydantic schemas validating all inputs.
  * Regex validation (`^[a-zA-Z0-9][a-zA-Z0-9._-]{0,127}$`) rejecting shell injection.
  * Field aliases supported (`culprit` / `culprit_service`, `target` / `target_service`).
- Configuration:
  * services/actuator-security/src/config.py: Environment variables with safe defaults.
  * Constant-time API key verification (`secrets.compare_digest`) via `X-API-Key`.
  * Allowlist enforcement: Culprits (`reviews-service,order-service,gateway-service`),
    Targets (`payment-vault,order-service,gateway-service`).
  * Protected services deny-list: `redpanda,redis,telemetry-collector,graph-engine,
    ml-detector,actuator-security,web-dashboard`.

2. IDENTIFIED PROBLEMS & SECURITY FINDINGS

--------------------------------------------------------------------------------
2.1 Problem 1 (HIGH SEVERITY): Container ID Authorization Bypass in Quarantine
--------------------------------------------------------------------------------
- Location: services/actuator-security/src/app.py, lines 224–257
- Problem Details:
  In `quarantine_service`, allowlist validation and protected-service checks are
  performed ONLY on `request.culprit_service`:
    if request.culprit_service in cfg.protected_services: ...
    if request.culprit_service not in cfg.allowed_culprits: ...
  However, the container passed to `eng.quarantine` is:
    container_to_isolate = request.container_id or request.culprit_service
  If a caller supplies:
    {
      "culprit_service": "reviews-service",
      "container_id": "redpanda",
      "target_service": "payment-vault",
      "reason": "Lateral movement"
    }
  The validation on `culprit_service` succeeds (because reviews-service is in allowed_culprits),
  but `eng.quarantine` isolates `redpanda` (a protected core infrastructure container).
- Impact:
  A caller could bypass allowlists or disconnect protected infrastructure services.

--------------------------------------------------------------------------------
2.2 Problem 2 (MEDIUM SEVERITY): Unconstrained Container & Network in Release Endpoint
--------------------------------------------------------------------------------
- Location: services/actuator-security/src/app.py, lines 340–366
- Problem Details:
  In `POST /api/v1/release`:
  1. `request.container_id` is never checked against `cfg.allowed_culprits` or `cfg.protected_services`.
  2. `request.network_name` can be specified by the caller (`request.network_name or cfg.docker_network`).
     A caller could reconnect a container to an arbitrary, unapproved Docker network.
  3. If `client.containers.get` or `client.networks.get` fails with a 404 in `containment.py:335`,
     the engine wraps it in a generic `ContainmentError`, which `app.py` returns as HTTP 500
     rather than HTTP 404.
- Impact:
  Unauthorized network attachments and unhandled 500 Internal Server Errors.

--------------------------------------------------------------------------------
2.3 Problem 3 (LOW SEVERITY): Inconsistent Action Label in Release Engine
--------------------------------------------------------------------------------
- Location: services/actuator-security/src/containment.py, lines 310 and 331
- Problem Details:
  Inside `ContainmentEngine.release()`, the return object sets:
    action="NETWORK_ISOLATION"
  Even though `app.py` overrides this in the HTTP response model to `NETWORK_RESTORE`,
  any internal log or engine caller sees `NETWORK_ISOLATION` during a release operation.
- Impact:
  Telemetry and log event inconsistency.

--------------------------------------------------------------------------------
2.4 Problem 4 (CONFIGURATION PREREQUISITE): In-Container iptables Missing NET_ADMIN
--------------------------------------------------------------------------------
- Location: services/actuator-security/policies/iptables_isolate.sh vs infra/docker-compose.testbed.yml
- Problem Details:
  `iptables_isolate.sh` executes `docker exec --user root "${CONTAINER}" iptables ...`.
  By default, Docker containers do not have `CAP_NET_ADMIN`. In `infra/docker-compose.testbed.yml`,
  testbed services (`reviews-service`, etc.) do not include `cap_add: [NET_ADMIN]`.
- Impact:
  Executing Mechanism B (`iptables_isolate.sh`) inside the testbed container will fail with
  "Permission denied (you must be root or cap_net_admin)".

--------------------------------------------------------------------------------
2.5 Problem 5 (ARCHITECTURAL LIMITATION): eBPF Program Lacks Userspace Loader
--------------------------------------------------------------------------------
- Location: services/actuator-security/policies/socket_drop.bpf.c
- Problem Details:
  The eBPF C program is syntactically valid C for a `cgroup_skb/egress` filter, but there is
  no Python `bcc`, `cilium/ebpf`, or `libbpf` loader script implemented to compile, load,
  and attach the bytecode to a container's cgroup.
- Impact:
  Mechanism C cannot be loaded or attached automatically without a userspace loader.

--------------------------------------------------------------------------------
2.6 Problem 6 (INTEGRATION LIMITATION): SPIFFE/SPIRE Workload Revocation is Simulated

- Location: services/actuator-security/pki/spiffe_revocation.py
- Problem Details:
  The module derives canonical SPIFFE IDs and tracks revocation in local memory, but does
  not execute a live gRPC call to a SPIRE Server API.
- Impact:
  Workload identity revocation is currently in audit/simulation mode.

    container_to_isolate = request.container_id or request.culprit_service

3.2 Solution for Problem 2 (Unconstrained Release Endpoint)
--------------------------------------------------------------------------------
File: services/actuator-security/src/app.py
Target Lines: 340–366

Proposed Code Fix:
```python
@app.post(
    "/api/v1/release",
    response_model=QuarantineResponse,
    tags=["containment"],
)
async def release_service(
    request: ReleaseRequest,
    _api_key: str = Depends(verify_api_key),
    cfg: ActuatorConfig = Depends(get_config),
    eng: ContainmentEngine = Depends(get_engine),
) -> QuarantineResponse:
    # 1. Enforce allowlist and protected-services check on release
    if request.container_id in cfg.protected_services:
        raise HTTPException(
            status_code=403,
            detail=f"Container '{request.container_id}' is protected infrastructure.",
        )
    if request.container_id not in cfg.allowed_culprits:
        raise HTTPException(
            status_code=400,
            detail=f"Container '{request.container_id}' is not an authorized testbed service.",
        )

    # 2. Restrict network strictly to the configured docker network
    target_network = cfg.docker_network

    # 3. Handle Docker 404 cleanly
    try:
        result = eng.release(
            container_id=request.container_id,
            network_name=target_network,
        )
    except ContainerNotFoundError as exc:
        raise HTTPException(status_code=404, detail=str(exc))
    except Exception as exc:
        raise HTTPException(status_code=500, detail=str(exc))
```
